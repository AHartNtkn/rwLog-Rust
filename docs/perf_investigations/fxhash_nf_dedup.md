# Investigation: FxHash for NF Deduplication

## Summary

Replaced `std::collections::HashSet` (SipHash) with `rustc_hash::FxHashSet` (FxHash) for all NF deduplication sets on hot evaluation paths. ~5% improvement on `recursive_even_backward_first64`, ~3% on `treecalc_first16`.

**Baseline:** 21.32ms (median, all values: 20.75, 21.34, 21.05, 21.44, 21.05, 20.88, 21.30, 23.98, 22.16, 21.59)
**After:** 20.24ms (median, all values: 20.32, 20.20, 19.71, 19.67, 19.85, 20.29, 20.34, 20.71, 21.06, 20.09)
**Improvement:** ~5.0% (same-session comparison)
**Mann-Whitney U:** 96/100 (p < 0.001)
**Regression:** None observed on treecalc_first16 (3% improvement, U=83/100)

## Problem

Profiling of `recursive_even_backward_first64` showed:
- `<core::hash::sip::Hasher<S> as core::hash::Hasher>::write` = 4.17% of total time

SipHash is a cryptographic-quality hash function designed to be resistant to hash-flooding denial-of-service attacks. For internal NF deduplication sets — where all keys are generated by the evaluation engine with no adversarial input — this security property is unnecessary and the computational overhead is pure waste.

NF hashing involves hashing SmallVec<[TermId; 1]> for match_pats and build_pats, plus DropFresh<C> including its SmallVec<[(u32, u32); 4]> map and constraint. SipHash's full mixing rounds on this data were consuming ~4% of execution time.

## Solution

Replaced `std::collections::HashSet<NF<C>>` with `rustc_hash::FxHashSet<NF<C>>` on all hot-path NF deduplication sets:

1. `DiagonalJoin::seen_l_set`, `seen_r_set`, `pending_set` — answer dedup in compose/meet joins
2. `Engine::answer_dedup` — global answer dedup in the engine iterator
3. `TableAnswers::dedup` — tabled answer dedup in fixpoint computation
4. `DedupQueue` — dedup queue used for answer streaming

### Key design decisions

1. **FxHash not just in diagonal.rs**: Expanding scope to all NF dedup sets (engine, fix, queue) contributed to the larger-than-expected gain. All these sets use the same NF Hash impl and are on hot paths.

2. **No changes to test code or cold paths**: Only hot-path HashSets were replaced. Test utilities and non-performance-critical code remain with std HashSet.

3. **No dependency changes needed**: The project already depended on `rustc-hash = "2.0"` for term store sharding, so FxHashSet was available without adding a new dependency.

## Files changed

- `src/work/diagonal.rs` — replaced HashSet with FxHashSet for seen_l_set, seen_r_set, pending_set
- `src/engine.rs` — replaced HashSet with FxHashSet for Engine answer dedup
- `src/work/fix.rs` — replaced HashSet with FxHashSet for TableAnswers dedup
- `src/queue.rs` — replaced HashSet with FxHashSet for DedupQueue
- `src/drop_fresh.rs` — fixed clippy comparison_chain warning
- `src/term.rs` — fixed clippy needless_lifetimes warning
- `src/constraint.rs` — fixed clippy unit_cmp warning

## Why 5% instead of 4%

The profiling showed SipHash at 4.17% self-time. The improvement slightly exceeds this because:

1. **FxHash has better cache behavior**: FxHash processes data in larger chunks (usize at a time) vs SipHash's more complex state machine, improving instruction cache utilization.
2. **Reduced branch mispredictions**: FxHash's simpler code path has fewer conditional branches.
3. **Scope expansion**: Replacing sets in engine.rs, fix.rs, and queue.rs (not just diagonal.rs) captured additional SipHash overhead not visible in the flat profile under the 4.17% entry.

## Remaining opportunities

- NF hashing still occurs on every answer emission. If answers could be identified by a cheaper key (e.g., a pre-computed fingerprint or term identity), hashing could be avoided entirely.
- The Hash impl for NF is derived, so it hashes all fields. A custom Hash impl that only hashes match_pats and build_pats TermIds (skipping constraint details when they're empty) could be faster for the common case.
