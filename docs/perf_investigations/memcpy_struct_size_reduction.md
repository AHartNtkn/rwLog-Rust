# Memcpy/Struct Size Reduction: Thin ChrState for ~8% Speedup

## Summary

Profiled the ~24.7ms baseline for `recursive_even_backward_first64` (execution-only). Found that **21-24% of engine time was in libc memcpy/memmove** from Rust value semantics moving large structs by value. The root cause was ChrState at 128 bytes inflating NF (224B), NodeStep (456B), and Node (232B). Restructured ChrState to use `Option<Box<ChrStateData>>` (16 bytes when empty), which cascaded through the type hierarchy to halve most struct sizes. Step_node's stack frame shrank from 2792 to 1384 bytes.

**Result: ~8% improvement on critical workload (24.7ms → 22.6ms). Cumulative ~4.5× speedup from original ~105ms.**

## Methodology

### Profiling: memcpy as the #1 Cost

The corrected execution-only profile (from the step_node_inline_control investigation) showed:

| Category | % of Execution |
|---|---|
| Memory copies (memcpy/memmove) | 21.2% |
| step_node dispatch | 26.8% |
| DiagonalJoin stepping | 9.1% |
| Drop overhead | 5.8% |
| Hashing | 3.9% |
| Clone (ChrState, DropFresh) | 3.2% |

Memcpy was the single largest remaining cost at the ~25ms baseline, generated by Rust's value semantics: returning NodeStep<C> (456 bytes) from step_node, passing Node<C> (232 bytes) between functions, and cloning NF<C> (224 bytes) throughout the engine.

### Root Cause: ChrState Bloat

ChrState<NoTheory> was 128 bytes despite containing only empty Vecs and VecDeques for the even/odd workload (no CHR constraints). This 128 bytes cascaded:

| Type | Size | ChrState Contribution |
|---|---|---|
| ChrState | 128B | 128B (100%) |
| DropFresh<C> | 176B | 128B (73%) |
| NF<C> | 224B | 128B (57%) |
| Node<C> | 232B | 128B (via NF) |
| NodeStep<C> | 456B | 256B (via NF+Node) |

For the even/odd benchmark, ChrState was always in its default/empty state — 128 bytes of zeros being memcpy'd on every step.

### Failed Approach: Boxing Individual Fields

**Hypothesis:** Boxing ChrStore (56B), TokenStore (24B), and VecDeque (32B) inside ChrState would shrink it from 128 to 40 bytes with minimal code changes.

**Result:** 22% REGRESSION (24.7ms → 30.3ms).

**Why:** Boxing individual fields traded inline memcpy for heap pointer chasing. The profile showed:
- libc memcpy dropped from 13.5% to 8.7% (good)
- But two new pointer dereferences appeared at 12.4% + 10.1% (bad)
- malloc appeared at 1.29% (3 allocations per ChrState clone)

The pointer indirections caused L1 cache misses. Stack reloads from a large frame hit L1 cache reliably because the stack is hot; heap pointer chasing does not.

### Successful Approach: Option<Box<ChrStateData>>

Moved all heavy fields into a single `ChrStateData<T>` struct behind `Option<Box<>>`:

```rust
pub struct ChrState<T: Theory> {
    pub program: Arc<ChrProgram<T>>,   // 8 bytes
    data: Option<Box<ChrStateData<T>>>, // 8 bytes (None when empty)
}
```

When ChrState is empty (the common case for even/odd):
- `data = None` → 0 heap allocation, 0 pointer chasing
- Clone: just Arc clone + None copy (16 bytes total)
- Hash: just program_id (no freeze_chr)
- Eq: just program_id comparison

|---|---|---|---|
| ChrState | 128B | **16B** | -87% |
| DropFresh<C> | 176B | **64B** | -64% |
| NF<C> | 224B | **112B** | -50% |

NF<C> (112B) is now very close to NF<()> (96B) — the ChrState overhead went from 128 extra bytes to just 16.

## Stack Frame Impact

step_node's stack frame (which includes inlined FixWork::step_in_place):

| Version | Frame Size | Deepest Stack Reload |
|---|---|---|
| Baseline | 2792 bytes | offset 0x600 (1536B) |
| After thin ChrState | **1384 bytes** | offset 0x3a0 (928B) |

50% frame reduction. Shallower stack reloads → better L1 cache hit rate.

## Implementation Details

### ChrState refactoring

1. Extracted `ChrStateData<T>` struct with all heavy fields (store, builtins, tokens, next_cid, agenda, failed)
2. ChrState reduced to `program: Arc<ChrProgram<T>>` + `data: Option<Box<ChrStateData<T>>>`
3. Added accessor methods: `data()`, `data_mut()`, `store()`, `has_data()`
4. Default creates `data: None` (no allocation)
5. Clone copies `None` trivially or deep-copies the single Box
6. Hash/Eq fast-path for `None` data (both sides empty → just compare program_id)

### Internal method restructuring

Methods that needed both `&self.program` and `&mut self.data` were refactored to associated functions taking explicit `(program, data)` pairs to avoid borrow-checker conflicts:
- `find_match` → `find_match_inner`
- `search_steps` → `search_steps_inner`
- `apply_rule_by_id` → `apply_rule_by_id_inner`
- etc.

### Key Insight: Boxing Granularity Matters

Boxing individual fields (3 Boxes) **regressed** performance because:
1. Three malloc calls per clone (vs. zero for None)
2. Three separate heap regions → poor spatial locality → cache misses
3. Pointer dereferences replaced stack reloads that were L1 hits

Boxing all data as ONE `Option<Box<ChrStateData>>` **improved** performance because:
1. Zero allocations for the empty case (None)
2. One contiguous allocation for non-empty (all data co-located)
3. No pointer chasing for the empty case (no Box at all)
