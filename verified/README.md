# Verified Rust

Rust code of the engine that is translated to Lean by
[Aeneas](https://github.com/AeneasVerif/aeneas) and proved against the
specification in `lean/RwLog`. This is where the verified engine that
replaces the interpreter in `src/` is built (roadmap M9, ledger L13 and L24).

```
rust/               the Rust crate `rwlog_core`
  src/store.rs      the base machine: a hash-consed store of term nodes, two tables
                    indexed by identifier, a stack of frames, and a tick counter
  src/term.rs       applying a binding, the occurs check, renaming, lists
  src/span.rs       the unifier, and `compose`, `meet` and the chain test on spans
  src/cover.rs      one-way matching, coverage without constraints, equality of spans,
                    the interfaces of a span
  src/sorts.rs      the declarations of sorts as lists of the store, membership,
                    conjunctions of sorts, one step of a conjunction, whether a
                    conjunction has a member, and inclusion in a sort, also but
                    for finitely many ground terms
  tests/            ordinary Rust tests of the same code, against a reference on trees
lean/
  RwlogCore/        generated by Aeneas from rust/src. Never edited by hand.
  RwLogVerified/    proofs about RwlogCore against lean/RwLog
  AxiomAudit.lean   the headline theorems use only Lean's three standard axioms
extract.sh          regenerates lean/RwlogCore
versions.env        the Aeneas, Charon, Lean and mathlib versions, upgraded together
check-versions.sh   checks that every file naming a version agrees with versions.env
```

## The base machine

`store.rs` is the machine every cost is counted on. A term is a node in the
store, and equal terms are one node, so a term is charged by its distinct
subterms and not by its size as a tree. One tick is one node read, one
allocation (interning included), one comparison of identifiers or words, or
one read, write or clearing of a table indexed by identifier, or one push,
pop or emptying of the stack. Nothing else in the crate can touch the tick
counter, and no other collection is used.

No function of the crate calls itself. A function that walks a term is a
loop: the nodes still to visit are frames on the stack of the store, and a
push or a pop is a tick like any other step. So the depth of a walk is paid
for in ticks and held in the store, and the machine's own call stack has a
fixed depth. `tests/no_recursion.rs` fails if the translation contains a
recursive definition, and `tests/deep.rs` runs every walk on terms and lists
four hundred thousand deep.

A variable is a node too: the base name, or the left or the right of a name.
Renaming a span apart is one allocation for each variable, and the names
read back as exactly the specification's `2v` and `2v + 1`.

## What is proved

Every theorem has the same shape: from any store that keeps the invariant,
holds the arguments and has room on its tick counter, the Rust function does
not panic, returns what the specification's function returns, only adds
nodes, and advances the tick counter by at most a stated amount.

### The bound for the unifier

`solveCost E o` (`RwLogVerified/SolveCost.lean`) bounds `solve_into` on the
equations `E` with the output term `o`. With `L` the number of equations,
`D` the distinct subterms of the equations and of `o`, and `V` the distinct
variables of the equations, it is

    10 + 8 D + 3 L + 12 lead + V (35 + 62 D + 28 L),    lead ≤ D.

The loop drops an equation between a term and itself (3 ticks), splits an
equation between two applications (9 ticks), or eliminates a variable, which
rebuilds every equation left and the output. A variable is eliminated at
most `V` times. Between two eliminations there are at most `D` splits. The
list never holds more than `L + D` equations, because the equations that
splitting adds are the right halves still pending along one path down a
term.

The bound is `V (D + L)` up to a constant, and it cannot be of a lower
order for this algorithm: an elimination rebuilds every distinct subterm
that is left and every cell of the list, and there are problems where every
equation eliminates a variable while the rest is still there. Composing the
identity on `n` variables with itself is one: the table below shows the
ticks spent growing with the square of `n`, as the bound does.

The constant is not the best possible. On that family the bound is about
fourteen times what is spent. Three things account for most of it: every
elimination is charged for the whole problem as it started and not for
what is left; every variable is charged an elimination, and here half of
them are eliminated; and each rebuild is charged every subterm at the full
price of an application that changes.

## The kernel rung

`rustKernel` (`RwLogVerified/Kernel.lean`) is a `Kernel Span Cost`
(`lean/RwLog/Trusted/Kernel.lean`). It returns what the domain of spans as
they are written returns (`rustKernel_refines`, against `Kernel.Refines
Domain.written`), as the specification kernel `Kernel.std` does, and its charge for `compose`, `meet`,
`composable`, `eq`, `rightBound`, `leftBound`, and `covers` when the covering
span has no constraints, is the tick bound of the table above
(`compose_realised` and its siblings). An engine runs at it with
`Engine.costedAt`, on the derivation kernel
`DerivationKernel.over Domain.written (rustKernel z)`.
`RwLogVerified/KernelRuns.lean` checks the charges of both kernels on a
worked composition; it runs no engine, because none is written against the
derivation kernel yet (`lean/PARKED.md`).

What is not derived, and why:

* `rep`, and `covers` when the covering span has constraints, keep the
  charges of `Kernel.std`. The domain of spans as written looks at no
  constraint; the kernel of the sorts replaces it (roadmap L39 and L48). Of
  the operations on sorts the store has membership, conjunctions, one step of
  a conjunction, pushing a sort down a pattern, whether a conjunction has a
  member and how many it has, inclusion, and inclusion but for finitely many
  ground terms so far, and not yet the normal store.
* The operations on nodes of the normal form and the rules that make answers
  (`DerivationKernel`) are charged as `lean/RwLog/Trusted/Charged.lean`
  postulates. They are not yet written on the store (roadmap L45).

`eqRel`, `canon`, `size` and `idSpan` are no longer operations of the kernel
(roadmap L30, L44).

Space. `Cost` has a space component. The store only grows and an allocation
is a tick, so an operation that may add nodes is charged its tick bound as
cells held; `span_eq` and `covers_plain` add no node and hold nothing.
`Realises` says so: an operation adds at most as many nodes as it holds
cells. The stack is empty when an operation returns, and while it runs its
depth is under the ticks spent, which is the peak of the charge.

What the theorems assume:

* Room on the tick counter: `40 * (ticks + bound) + 100` fits in a `usize`.
  The node, table and stack indices are bounded through the ticks (roadmap
  L43, counter overflow).

## Rules for the Rust

The crate is written in the subset Aeneas translates to definitions that can
be reasoned about. Found by trial at the pinned commits:

* Single-threaded, safe Rust. No `Rc`, `RefCell`, `Arc`, atomics.
* No `dyn Trait`, stored closures or function pointers. Generic traits and
  closures passed to generic functions are fine.
* Data in `Vec`, structs and enums. No `HashMap`, `BTreeMap`, `VecDeque`: a
  table is written by hand over `Vec`.
* Loops over indices. Use `break` or a result variable where a loop would
  return from several places.
* No recursion. A walk over a term is a loop over the stack of the store.
* The only code that may touch the tick counter or the fields of `TermId` is
  `store.rs`.
* All data lives in the store, its two tables and its stack. No function
  outside `store.rs` owns a `Vec` or any other collection.

## Building

```
cd verified/rust && cargo test --no-run && timeout 10 cargo test
cd verified/lean && lake exe cache get && lake build --wfail
```

The Lean build needs neither Charon nor Aeneas, because the generated files
are committed.

## The generated Lean follows the Rust

After changing `rust/src`, run `./extract.sh` and commit what it writes to
`lean/RwlogCore`. CI (the `extraction` job of
`.github/workflows/verified.yml`) fetches Charon and Aeneas, runs
`./extract.sh --check`, and fails if the committed files differ from what the
Rust translates to. So on any commit where CI passes, the theorems are about
the Rust in `rust/src`.

`extract.sh` needs `charon` and `aeneas` on `PATH` and refuses to run unless
they were built from the recorded commits. The header of `extract.sh` gives
the `nix shell` command that fetches or builds both. Building them takes about
a quarter of an hour; CI keeps the built tools and reuses them until
`versions.env` changes.

## Versions

`versions.env` is the one record of the Aeneas commit, the Charon commit, the
Lean version and the mathlib version. They are upgraded together, in one
commit: each Aeneas commit works with one Charon commit and one Lean and
mathlib version, and `lean/` and `verified/lean` build as one Lean project.
The files that have to repeat a version (`lean-toolchain`, `lakefile.toml`
and `lake-manifest.json` in `lean/` and `verified/lean`) are compared with
the record by `./check-versions.sh`, which also checks the record against
what the Aeneas commit itself asks for. CI runs it on every change to
`lean/` or `verified/`.
